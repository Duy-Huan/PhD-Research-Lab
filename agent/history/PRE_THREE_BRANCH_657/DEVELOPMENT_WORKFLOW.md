# Shared feature and repair workflow

1. Read AGENTS.md, agent/AGENT.md, current STATE/PLAN, ZERO_FAKE_TESTING_POLICY and CI_CD_AUTOMATION.md. Never delete skills/ or agent/. Historical detail is linked from agent/history; read only relevant records.
2. Before a new feature, search GitHub for relevant skills, review/pin provenance and licenses, install appropriate reviewed skills under skills/ and record SOURCES.json. Reuse already pinned suitable skills; do not install unreviewed code or claim a skill certifies software.
3. Preserve git status/diffs/user changes. Use a task branch and isolated worktree, record source/base SHA, and synchronize with actual dev as authorized. Preview main/dev/qa is untrusted; do not overwrite newer integrated application source with the old preview. Only one integration task edits CI/gates at a time.
4. Define a reviewed Feature Quality Contract and meaningful executable acceptance tests. Record genuine RED/GREEN evidence and scope; retrospective comparisons are not invented development chronology. Preserve API/SSE, research integrity, project containment and locale behavior.
5. Use python scripts/verify.py quick or targeted while coding. Read bounded fingerprints/raw relevant logs, not every successful stack trace. A repair task/PR gets at most3 automatic CLI invocations; stop on actual unavailable prerequisites, never reset counters or change assertions for green.
6. Before normal task-branch push, run canonical feature with stable source, then commit exact scoped changes and open/update a PR into dev. A deliberately failing isolated acceptance fixture may be pushed only under an explicit owner-requested red exercise, clearly labeled; it cannot bypass merge gates.
7. Inspect actual GitHub run/checks/artifacts for the exact latest PR head. Owner-authorized local CI Repair Supervisor may assign a registered CLI to exact source paths and immutable test IDs. It runs targeted plus feature verification, commits/pushes to the same branch and confirms fresh CI. Read CI_REPAIR_SUPERVISOR.md for trust/state/start/stop.
8. Request only native GitHub auto-merge for eligible trusted dev PRs after genuine mandatory checks/jobs. No admin bypass, force push, arbitrary fork repair or automatic qa/main modification. Verify actual merged flag, commit SHA and inclusion in dev. Repo flag/unit fixtures alone are not proof.
9. Owner-controlled dev?qa promotion requires full regression and current-source real provider/research/AI-UAT qualification. Missing/skipped/unsupported layers block. Use authorized local Spark where supported; do not silently substitute models, spend paid credits or exceed the exhausted UAT repair budget.
10. Only qualified QA may create qa?main PR. Native protection/owner approval controls main. Separate main-push CD verifies QA provenance/tree, packages checksummed source/web assets and publishes GitHub Release. PC update is controlled with data backup/rollback; local verification never grants publication authorization.
11. Update concise state, evidence, defect inventory, versions and user guide. Compare branches only with the same frozen test suite/environment/policy and fixed critical denominators. Never call mocked/unit/DOM-only output live AI or scientific validation, and never claim an entirely bug-free application.
