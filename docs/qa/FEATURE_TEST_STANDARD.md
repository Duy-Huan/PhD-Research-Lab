# Feature quality and test standard

Each new feature has a reviewed JSON contract under contracts/, requirement IDs, observable acceptance criteria, negative/boundary/recovery cases and executable test traceability. [The human template](templates/FEATURE_CONTRACT.md) explains the fields; `scripts/generate_test_matrix.py` exports the matrix from an actual contract and marks absent/stale executions UNVERIFIED. Generating rows is not executing tests or proving all behavior is covered.

Test first where behavior can be reproduced: preserve actual RED runner output, repair implementation, then preserve GREEN of the same failing test IDs. `validate_tdd` verifies artifact hashes and that failed IDs execute successfully afterward; an import/bootstrap RED must be labeled honestly and cannot masquerade as a functional regression. The verification-infrastructure contracts include functional malformed-input and resource-bound RED/GREEN examples. Existing application history is not retroactively certified by those examples.

Risk drives scope: LOW uses deterministic affected checks and smoke; MEDIUM adds affected integration/E2E; HIGH includes error/recovery and necessary browser exploration; CRITICAL adds real integration, comprehensive relevant acceptance, independent review and explicit release authorization. Shared provider/memory/API/CI policy or unknown dependencies broaden selection. Mandatory PR/full gates never use an incremental subset.

Use equivalence classes, boundaries, decision/state transitions, properties, API contracts, fault injection, persistence and concurrency where they can distinguish correct from incorrect behavior. Avoid assertion-free, implementation-mirroring or expected-output-copying tests. AI findings become regression tests only after controlled reproduction; unconfirmed findings remain visible. Deliberately broken UI fixtures are harness self-tests, not product bugs or research results.

Testing documentation and traceability are informed by [ISO/IEC/IEEE 29119-3:2021](https://www.iso.org/standard/79429.html) and the [29119 series](https://committee.iso.org/sites/jtc1sc7/home/projects/flagship-standards/isoiecieee-29119-series.html). Quality criteria use the [ISO/IEC 25010:2023 product-quality model](https://www.iso.org/standard/78176.html); secure development practices refer to [NIST SSDF 1.1](https://csrc.nist.gov/pubs/sp/800/218/final). This repository has not undergone a formal standards-conformance certification or audit of the complete copyrighted standards.
