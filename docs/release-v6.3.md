# v6.3.0-preview.1 — bounded collaboration

See [architecture/API/operator guide](architecture/v6.3_multi_team_collaboration.md), [readiness audit](audits/v6.3_readiness.md) and [final validation](../artifacts/v63/validation.md). The implementation extends the v6.0/v6.2 control plane in separate versioned commits and remains opt-in experimental. Logical teams share one bounded worker; they are not independent top-level orchestrators or guaranteed scientific reviewers.

Harness: `.venv/Scripts/python -B tools/research_harness.py --stage 6.3`. Eight actual local Mission executions compare a single adaptive team with automatic multi-team partition on three fixed workflow families. Literature intentionally stays one team; two native file branches partition into three domains; literature plus CPU/review/report branches partition into four. All technical workflows completed with simulated human gates, actual bounded CPU trials, independent raw metric checks and matching fresh-process reproduction. Scholarly metadata/workspace contents are labelled synthetic. No model inference, provider spend or GPU work was submitted.

The exact latest timings, task counts and logical-role/domain counts are generated in [benchmark.md](../artifacts/v63/benchmark.md) with the JSON trace. Literature uses 2 tasks and one domain on both paths; workspace reconciliation uses 3 tasks and 1 vs 3 domains; literature plus CPU uses 4 tasks and 1 vs 4 domains, repeated with new approvals.

These small, serial samples show added collaboration bookkeeping rather than a speed advantage. Default multi-team remains off; use it when explicit contracts, evidence receipts and review separation are useful. No statistically generalizable scientific quality/performance improvement is claimed. Every row records technical completion, observed wall time, task/role/domain counts, retries, review actions, null opaque provider costs and zero GPU time. Unit fault injection separately measures denial/recovery cases; these are not fabricated into a live provider benchmark.

Adversarial acceptance covers stale canonical writes with no overwrite, distinct task files, wrong receiver/forged schema, idempotent publish/receipt after downtime, cross-Topic/project denial, audited authority escalation, central one-GPU admission and fixed-protocol GPU rejection, failed OpenScience workspace leaving Feynman state unmodified, provisional unsupported findings, automatic verifier dispute, versioned PI resolution and final-review blocking. Existing scientific checks still reject corrupted metrics, wrong source evidence and protocol drift. Full details/counts are in the validation artifact.

Schema 7 saves a v6 backup. Task report paths now include task identity; historical recorded artifact paths remain valid. Rollback and operational controls are in the architecture guide. No user project or native engine configuration is reset by upgrade/harness.

Open gates: real bounded scientific pilot and human signoff, live scholarly/citation services and native model tasks, authenticated remote team transport, general multi-Topic execution within one Mission, parallel execution, arbitrary scientific code/GPU training and pinned Docker containment/escape qualification. Automatic publication, expensive uncontrolled execution and silent memory promotion remain disabled. Night operation requires the app, machine and authorized services to stay running.
