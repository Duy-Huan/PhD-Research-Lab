# v6.2 team harness and composition

Audit/design gate: [v6.2 readiness](../audits/v6.2_readiness.md). v6.1 was absent; this release supplies the smallest compatibility layer on `mission_tasks`, `mission_attempts`, the existing project worker and resource governor. There is no second top-level orchestrator, model framework or memory store.

`research_os.team_enabled=false` by default. Enable Research OS and teams explicitly. `MissionSpec.team` contains strict `TeamPlan`, logical `AgentRole` capabilities/permissions/engines/purpose/expected value/termination, and exactly one `TaskAssignment` per DAG node. Existing `Task`, `Limits`, capability descriptors, ExecutionResult and VerificationResult supply task/resource/output contracts. Unknown fields, duplicate owners, excessive agents, cycles, unknown capabilities, permission/engine escalation and self-verification are rejected.

Templates: **single** uses one worker plus an independent verifier when necessary; **fixed** assigns ordinary work to up to two worker roles plus required verification; **adaptive** starts with one worker, adds an independent verifier for scientific tasks and a compute specialist only for a genuinely independent compute branch. Roles are logical ownership domains sharing providers serially, not always-running model processes. `max_agents≤4`, `max_parallel_tasks=1`, inherited attempts/depth/hops/time/call limits and at most two replan generations are hard upper bounds. Parallel task execution is intentionally unqualified.

Proposal adds explicit deterministic `experiment.verify`/`artifact.verify` nodes for scientific work. They use original arrays/metrics/hashes and raw run records, not the worker's self-review. First compute without a distinct reproduction remains unverified; a matching independently checked run can satisfy deterministic verification. A comparison claiming improvement without metrics/artifacts remains unverified. Artifact integrity alone does not certify semantic entailment or scientific validity. Mission completion and claim approval remain distinct.

Every dependency handoff is a versioned `TaskEnvelope` containing mission/Topic/task, sender/receiver, dependency ID, input-result digest, artifact references and untrusted status. It is inserted transactionally at admission with a unique dependency key and immutable snapshot. It passes selected pointers rather than whole chat histories. Execution records retain owner/verifier, observed queue/elapsed time, outcome and attempt key. Native session/run identities remain in existing result provenance; missing usage is null. Registry statistics are exact observed task counts by capability/outcome, not invented confidence scores. Backend health is rechecked at admission.

Failure reassignment supports known failed/unadmitted reasoning tasks only. It cannot expand permitted engines or billing policy, bypass an uncertain admission, reset consumed reasoning/time budgets or exceed generation caps. Completed tasks are excluded and scoped paper inputs resolved into the new draft. Other kinds needing a more complex handoff require manual versioning. New plans always require fresh human approval; there is no automatic paid retry after quota exhaustion. Cooldown and existing resource slots still apply. A manual new scientific budget/direction requires a new reviewed brief.

API under `/api/research`: GET `/team-capabilities`; POST `/teams/propose?mode=single|fixed|adaptive` with MissionSpec returns an editable spec, starts nothing; POST it to the existing Topic Missions endpoint to create a draft. GET `/topics/{tid}/missions/{mid}/team` returns attempts, handoffs and actual active admissions. POST `.../replan` `{task_id,engine,note}` creates a new unapproved version. Existing pause/cancel/approve/retry/review controls remain authoritative. `/team` opens the contextual UI with editable proposal JSON, role rationale, ownership, permissions, status and handoffs. All controls are direct HTTP actions with zero inference calls.

Schema 5→6 adds immutable `task_handoffs` and saves `research.v5.sqlite3.bak`. Rollback: stop app, archive current project/artifacts, restore that backup alongside v6.0 code. Disable the team flag to stop new team admissions without losing records. Historical v5/6.0 missions remain usable.

Validation: eight team tests cover minimal literature, real CPU verification/reproduction, privilege escalation/self-review, unavailable OpenScience with no paid admission, quota and budget-preserving replan drafts, pause/restart, unsupported performance claims and Topic isolation. The harness `python -B tools/research_harness.py --stage 6.2` executes the same three workflow families through single/fixed/adaptive paths (12 actual Mission executions including reproduction), preserves raw CPU/log/audit evidence and records wall time/execution count/retries/review actions/unknown cost. Fixture literature and workspace files are labelled synthetic. The measured test does not establish that adaptive teams outperform single workers, especially with serial execution and no model reasoning workload. See artifacts/v62/harness.json and measurements.zip.

Security limits: trusted local researcher API, no independent authenticated machine-agent identities, no automatic publication or memory promotion, no live scientific pilot/provider inference/GPU/container escape qualification. v6.3 must preserve these boundaries when adding workstreams; defer multi-team whenever a single team suffices.
