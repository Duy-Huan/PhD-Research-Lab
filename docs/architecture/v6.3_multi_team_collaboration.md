# v6.3 multi-team collaboration and operator guide

Readiness gate: [audit](../audits/v6.3_readiness.md). Baselines: v6.0 `312e9b0`, v6.2 `40e1173`. The single Mission worker remains the sole top-level authority. No team can create another global planner, launch unregistered tools or promote conversations into memory. Skills, native providers, Paper Explorer, SKB and the existing resource governor remain in use.

## Workstream admission

`MissionSpec.collaboration` adds a strict `CollaborationPlan` of ≤4 `Workstream` charters. Each declares Topic, objective, exclusive task membership, exact inter-team dependencies, deliverables/evidence requirements, engine/permission subsets, reasoning/time/storage allocation. Allocations sum to no more than the Mission limits. Every task has one owner role from the existing TeamPlan and belongs to exactly one workstream. Workstreams can share the same logical provider role serially; a team is not a fabricated running model process. The independent verifier remains a separate deterministic role/task.

Automatic partition requires at least two independent substantive roots; two native file-reconciliation roots also qualify. Domains group literature, experiments, independent verification, reporting and each workspace branch. The task and workstream graphs must both be acyclic; insufficient budget, no useful independence or a grouping cycle falls back to a single team. Manual charters are editable before exact-plan approval. A simple literature search never starts Docker or creates unnecessary teams.

`research_os.enabled`, `team_enabled` and `multi_team_enabled` all default false. The first two must be enabled for team execution; the third is required for more than one workstream. Disabled flags pause admission while retaining history. All selected engines and API/opaque native billing permissions are still bound by the approved Mission brief. Changing charters/goals/budgets requires a fresh reviewed Mission version. Automatic v6.2 reassignment stays limited to single-team Missions; uncertain workstream side effects must be reconciled rather than reissued under a different team.

Each Mission remains owned by one Topic. Multiple Topic Missions under a project charter keep files, approvals, native sessions and messages isolated. Directed charter retrieval grants permit only report reads from named Topics; they do not authorize cross-topic execution/handoffs or file writes. General one-Mission multi-Topic execution and remote authenticated team transport remain intentionally deferred.

## Durable evidence protocol

`WorkOrder` includes project/Topic/Mission, source and target teams/tasks, expected ExecutionResult schema and an `EvidenceBundle` of source/run IDs, artifact path/hash/byte references, original result digest and unverified trust. The producer publishes cross-team task dependencies transactionally with completion. A unique `(mission, source task, target task)` key prevents duplicate publication. Before receiver admission, the service validates schema, project/Topic, dependency, target team, current producer-result digest and owned file checksums, then commits one immutable receiver receipt. No whole conversation history or free-form chat is the sole transport.

Published messages and receipts survive restart. If shutdown occurs between committed tasks with no uncertain admission, the existing approval resumes at the next pending node. If an actual task admission was in flight, it becomes interrupted and never automatically repeats. Paused/cancelled Missions remain paused/cancelled; uncertain tasks still require reconciliation. A corrupt handoff pauses visibly instead of being accepted based on a model's statement. Team handoffs supplement existing immutable role-level TaskEnvelopes and attempt records rather than replacing them.

Native workspace sync records exposed file versions/checkpoints; private native sessions/reasoning remain unobservable. Native engine invocations preserve existing run/session IDs when the adapter returns them. CPU protocols retain code/dataset/environment/seed fingerprints and raw metrics, with independent deterministic verification and fresh-process reproduction. Missing measurements or unsupported interpretations remain unverified. Credentials and subscription tokens are not extracted.

## Shared outputs and scientific review

Each task report is now stored at `workspace/research/missions/<mission>/<task>/evidence-report.json`, so two teams cannot silently overwrite the same file. Canonical output registration stores a hash-checked reference, not an arbitrary team-selected write path. `(Topic, output key)` is updated only if `expected_revision` matches. Competing stale writes fail, preserve the winner and append an audit conflict. Every successful replacement requires a human note and retains an append-only revision. There is no endpoint to erase canonical history, receipts or messages.

Findings reuse v5.6 ClaimInput/evidence/source checks. A team submission creates proposed/sourced content; it never certifies itself or writes trusted memory. Deterministic review returning failed/unverified opens a durable dispute. A PI can submit additional scoped claim disputes and resolve them with an expected revision and note. Final Mission review is blocked until open disputes and unacknowledged handoffs are resolved. Resolving a dispute records follow-up/acceptance of technical workflow only; it does not approve the scientific claim. Scientific human approval still uses the separate v5.6 gate.

The authenticated actor boundary remains the existing local trusted researcher application. Team identifiers are server-derived from the approved plan and not new independently authenticated remote accounts. Agent tools do not receive these administrative APIs. OS administrator access or direct calls under the researcher's identity can replace authority; this release does not claim security against that threat. Keep independent backups of the hash-linked ledger.

## Resources and backpressure

One task dispatch at a time; teams are logical domains, not concurrent GPU models. Existing global CPU/GPU/local-model/CLI/cloud slots are reused. Each workstream has persisted reasoning, elapsed execution and artifact-byte accounting. Both admission and output settlement enforce the narrower charter. Trusted denoising observations and worst-case PDF download sizes have a conservative storage preflight; newly stored PDF bytes are charged on success or failure. Topic corpus quotas still apply. Counters cover declared artifacts, not an OS quota for SQLite/index/log overhead. Timeout is the minimum remaining Mission/charter/workstream/deadline budget. Artifacts from failed output checks are retained and never trigger an implicit retry. GPU requests are rejected by the new fixed protocol; the existing GPU governor admits at most one GPU holder.

Quota errors consume the actual admission and establish the existing 15-minute project/provider cooldown. No undocumented quota estimate, billing fallback or retry storm is used. Token/currency usage remains null when opaque. Cross-project provider breakers remain separate (conservative explicit per-project calls); hardware slots are process-wide. Live GPU, general code training, memory/network containment and Docker escape acceptance are not qualified by this preview.

## API and UI

All research routes bind the current project for the request. Under `/api/research`:

- POST `/workstreams/propose?max_teams=4` with MissionSpec returns an editable proposed spec and starts no execution. Submit it through the existing Topic Mission create/approval path.
- GET `/topics/{tid}/missions/{mid}/workstreams` returns charters, actual task states, usage, evidence messages, receipts, disputes and canonical references.
- POST `.../handoffs` `{source_task,target_task}` publishes only a declared completed dependency; POST `.../handoffs/{id}/ack` `{receiver_team}` validates/acknowledges it. Normal execution performs these transactionally without an LLM.
- POST `.../outputs` `{team_id,key,source_task,artifact_index,expected_revision,note}` performs optimistic canonical registration.
- POST `.../findings` `{team_id,text,kind,evidence}` creates a provisional scientific claim; supplied actor/status fields are rejected.
- POST `.../disputes` `{team_id,note,claim_ids}`; POST `.../disputes/{id}/resolve` `{expected_revision,note}` records a human resolution.
- GET/PUT `/os-settings` controls the three experimental flags. Existing Mission pause/approve/retry/cancel/review and artifact APIs remain authoritative.

Use `/workstreams` inside the existing chat drawer. Inspect per-team tasks, limits and observed resource use; open evidence bundles/receipts, canonical revisions and disputes. PI decisions and output registration use direct HTTP controls with no inference. Mission Monitor provides pause/resume and exact-plan review. Existing Workspaces drawer opens supported native workspaces. The chat composer and `/skills` are preserved. No fake percentage progress or real-time engine activity is displayed.

## Migration and rollback

SQLite 6→7 adds workstream counters, immutable messages/receipts, disputes, canonical pointers and append-only history, retaining `research.v6.sqlite3.bak`. Existing data and settings are retained. Disable multi-team to block new multi-team admissions while retaining records. To roll back: stop the app, archive the entire project and current artifacts/DB, check out v6.2 code, restore `research.v6.sqlite3.bak` to `research.sqlite3`. A v5.6 rollback instead needs schema4 and its code. Earlier runtimes refuse newer schemas. Do not discard post-backup decisions or merge newer rows into an old schema silently.

A direct upgrade from v5.6/schema4 creates `research.v4.sqlite3.bak` and advances directly to schema7; intermediate v5/v6 backups are not fabricated. Use the backup that matches the actual previous installation, with compatible code, and retain the new DB/artifacts separately before rollback.

Acceptance and measurements: [release guide](../release-v6.3.md), `artifacts/v63/harness.json`, original hash-verifiable audits/raw arrays/logs in `measurements.zip`, and final validation report. This is an experimental preview; a bounded live scientific pilot and external execution qualification remain release gates for stable research autonomy.
