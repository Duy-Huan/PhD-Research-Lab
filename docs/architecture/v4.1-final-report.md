## 2. Model lifecycle (the urgent request)

Settings → **Model lifecycle & resources** (also a live "In VRAM now" list at the top of Settings → Local AI).

| Class | What "loaded" means | Policies |
|---|---|---|
| Local AI — background tasks (summarizer, critic, PDF parser, embeddings, workflow agents) | weights in VRAM | **Load → task → unload** (default), Keep loaded, Unload when idle |
| Local AI — chats | weights in VRAM | Unload when idle (default, 10 min), Keep loaded, Load → task → unload |
| CLI agents | resumable native session (the process always exits) | same three options (Keep = resume next question) |
| MCP AI tools & sandbox container | Docker container running | same three options |
| Cloud AI | pooled HTTPS connections | same three options (Load → task → unload = new connection per call) |

Safety: a model with an active lease is never unloaded; models you loaded yourself are never auto-unloaded
(option); only one PhD-Lab model in VRAM at a time (option, avoids VRAM spill on 12 GB); a 15 s grace after a task
prevents load/unload thrashing in bursts; Ollama is pinned (`keep_alive -1`) so its own 5-minute default does not
override your policy. The live panel shows GPU VRAM, each resident model (engine, VRAM, owner, state, countdown) with
**Unload** / **Unload all**, tracked CLI/MCP/cloud resources with **Release now**, and the last actions. It polls
only while Settings is visible and the browser tab is in the foreground. Opt-in: *Free VRAM automatically before a
GPU training run* (idle models only; otherwise the v3.2 rule — refuse until you unload — stays).

## 3. Secure CLI gateway (Firewall spec M1)

* cwd is always `<data>/cli-space/<provider>/sessions/<gateway session>/workspace/` (configurable root), never the app
  or project folder; verified by tests.
* Environment rebuilt from an allowlist; tokens/keys/cloud credentials dropped; provider API keys pass only with the
  existing `<provider>_api_fallback` switch.
* Profiles: `review` (default, read-only) and `assisted` (session workspace writable). Codex enforces both with its OS
  sandbox; Claude Code `assisted` is permission-based only (no OS sandbox on Windows) → **needs explicit consent per
  request**; Gemini/Antigravity `assisted` → **refused** (fail closed).
* Context bundle + manifest (sha256, included ids, sensitivity, profile, isolation level) staged **read-only** in
  `context/`; answers in `output/`; redacted stderr in `logs/`; bounded retention (14 days / 300 sessions).
* Connector time limit (`gateway.provider_timeout_s`) and process-tree kill on cancel, timeout or client disconnect.

Limitation (honest): on Windows, directory isolation is not a sandbox — read isolation depends on the vendor's sandbox
(Codex) or permission system (Claude Code, Gemini, Antigravity). The isolation level is shown and stored per session.

## 4. Workflow orchestrator

* **Modes:** manual (every result reviewed, consequential steps wait), assisted (default; low-risk work automatic,
  agent proposals reviewed, high-risk steps wait), bounded automation (requires explicit trial / runtime / cycle
  budgets; stops at configured gates), custom (autonomy per step). Any step's autonomy can be overridden without code.
* **Decisions:** Approve, Edit (parameters before / result after — re-validated), Revise (agent re-runs with your
  note), Reject, Provide result (you did the step yourself).
* **Budgets** are a ledger on the root run shared by nested runs: trials, cycles, agent calls, runtime → BUDGET_EXCEEDED.
* **Recovery:** after a restart, running runs become PAUSED; idempotent steps retry, an HPO study continues from its
  checkpoint, any other step asks you before re-running; completed steps never re-run.
* **Templates:** research planning, model feasibility audit, search-space design, HPO, multi-objective, failure
  diagnosis, researcher-led experiment, full bounded loop (nested + `workflow.repeat`), ablation, candidate
  confirmation, planning → feasibility → search space (nested, Scenario H).
* **Honesty rules:** AI output labelled AI_SUGGESTION / AI_INTERPRETATION; synthetic benchmark objectives labelled
  SYNTHETIC; memory writes are review **candidates** only; search spaces are data (never `eval`).
* **Performance on a consumer PC:** one execution step at a time (sandbox/GPU), GPU trials always sequential, Optuna
  storage cached per process (one SQLite pool), SSE + debounced refresh in the UI, no stream while the page is hidden.

## 7. Migration / rollback

Additive only: new config sections (`lifecycle`, `features`, `workflow`, new `gateway.cli_*`,
`resources.auto_unload_for_gpu`) get defaults; v4.0 config files load unchanged. New data lives in
`<project>/workflows/` and `<data>/cli-space/`. Rollback: switch `lifecycle.enabled` / `features.*` off (v4.0
behaviour), or check out v4.0 — the new folders are simply ignored. The CLI cwd change is the only behaviour change
that cannot be switched off (security fix); a provider that needs to read project code should get it through the
compiled context or MCP tools.

Dev tools added to `.venv` (not runtime requirements): `coverage`, and `optuna` (optional runtime HPO engine;
without it the builtin random/grid engine is used) — see `requirements-dev.txt`.
